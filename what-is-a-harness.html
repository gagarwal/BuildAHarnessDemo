What is a harness?

From one-shot prompts to long-running agents.

The arc

Four ways to use a model

1 · one-shot

One-shot call

One prompt in, one answer out. No memory, no tools, no second look.

2 · chain

Prompt chain

A fixed pipeline you wire by hand. Deterministic, but no feedback or recovery.

3 · agent loop

Agent loop

The model picks each next action, acts through a tool, observes, repeats until done.

4 · harness

Harness

Scaffolding around the loop: tools, durable state, recovery. Runs across many windows.

Each step adds one thing the previous one could not do. This deck walks the whole arc, then you build a small harness yourself.

The arc · 1 of 4

One-shot: a single pass

Great for

  • Self-contained answers
  • Classify, extract, rewrite, summarize
  • Anything that fits in one window

Falls over when

  • The task needs to touch the real world
  • It is bigger than one context window
  • The first attempt is wrong and nobody checks

The arc · 2 of 4

Prompt chaining: a fixed pipeline

  • You decide every step in advance. The model never chooses what to do next.
  • Deterministic and easy to reason about, which is exactly why it is brittle.
  • No feedback loop: if Step B produced garbage, Step C runs on garbage anyway.
  • Works until the task stops being a straight line. Real work rarely is.

The arc · 3 of 4

The agent loop: the model drives

  • Unlike a chain, the steps are not scripted. Each turn, the model chooses the next action.
  • It acts through a tool, the harness runs it, the result returns, and the model decides again, looping until it judges the task done.
  • That autonomy is the leap from "run my script" to "an agent." The loop is the engine, and it is also where long tasks go wrong.

The arc · 4 of 4

What a harness actually is

Everything around the model that turns a single answer into sustained work. Agent = model + harness.

The agent at work

  • The loop: the model picks an action, a tool runs it, the result returns, repeat.
  • Tools: how it touches the world: files, shell, browser, MCP.
  • Context & memory: durable state (git, progress file, session log) plus resets.

The control around it

  • Guides (feed-forward): prompts, specs, conventions that steer before it acts.
  • Sensors (feedback): tests, linters, evaluators that correct after it acts.
  • Recovery: retries, resets, wake() from a durable log, sub-agents.

None of this is the model. It is the scaffolding that makes the model dependable. Next: how it fits together.

Definition · the shape

A harness is the scaffolding around the loop

The model stays the same. The harness is everything around it: guides that steer before, sensors that correct after, durable context, and the tools it acts through.

Read more: martinfowler.com/articles/harness-engineering.html · openai.com/index/harness-engineering

Why scaffolding · 1

The real constraint: the context window is finite

Every tool result, file, and reasoning step accumulates in the window. On a long task it fills up. What the model does as it approaches the limit is the whole game.

Why scaffolding · 2

Two failure modes near the limit

Over-ambition

  • Tries to finish the entire project in one window
  • Runs out of context mid-build
  • Leaves half-implemented features and broken state

Premature completion

  • A fresh session declares the work "done"
  • It cannot see what is actually missing
  • Real functionality is still absent

Models show "context anxiety": as the window fills, they rush to wrap up. Anthropic, Harness design for long-running apps

Why scaffolding · 3

Reset beats compaction

  • Compaction keeps continuity but never gives a clean slate, and detail erodes each pass.
  • Reset clears the window and rebuilds from a durable handoff, so the agent starts sharp every session.
  • This mattered a lot for older models and less for newer ones. Re-test your assumptions as models improve.

Harness anatomy · Pattern A

Initializer + coder

  • One agent initializes the durable artifacts once. Every later session is a coder that resumes from them.
  • The discipline that prevents the two failure modes: one feature per session, tested end to end, then committed. Git is the source of truth.

Read more: anthropic.com/engineering/effective-harnesses-for-long-running-agents

Harness anatomy · Pattern B

Planner → generator → evaluator

  • Separation of concerns. An independent evaluator catches what a self-grading generator talks itself past.
  • Evidence of the payoff: a retro-game build went from 20 min / $9 / broken solo to 6 hr / $200 / playable under the full loop.

Read more: anthropic.com/engineering/harness-design-long-running-apps

Harness anatomy · Pattern C

Managed agents: brain, state, hands

  • Decouple the three. A crashed brain restarts with wake(sessionId); a dead container is just a tool error the brain handles.
  • State lives outside the window (getEvents()), secrets never reach the sandbox, and skipping needless provisioning cut time-to-first-token ~60% at p50.

Read more: anthropic.com/engineering/managed-agents

The load-bearing idea

A harness encodes what the model can't yet do

"Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing." Anthropic, Harness design for long-running apps

  • Sprint decomposition, context resets, hand-holding prompts: each is a workaround for a current limitation.
  • As models improve, strip the harness down. Anthropic removed reset logic once a newer model stopped needing it.
  • Fowler's framing: the steering loop. When an issue recurs, add a guide (before) or a sensor (after) so it cannot recur, and remove the ones the model outgrows.

Decision · restraint

When NOT to build a harness

  • The task fits in one window and one pass. A harness just adds latency and cost.
  • The cost tax is real: the same job was $9 and 20 minutes solo versus $200 and 6 hours under a full harness.
  • Reach for a harness when the work is long, open-ended, and must touch real systems, where being correct beats being cheap.
  • Start with the smallest loop that works. Add a planner or evaluator only when you can point to the failure it fixes.

Recap

The story so far

  • One-shot and chains hit a wall: no memory, no tools, no feedback, no recovery.
  • A harness wraps the agent loop with guides, sensors, durable context, and tools.
  • It exists to beat two failure modes: over-ambition and premature completion, both driven by the finite window.
  • Three proven shapes: initializer + coder, planner / generator / evaluator, managed brain / state / hands.
  • Keep it minimal and re-test it as models improve. Now let's build one.

Tutorial

STEP 1 Setup and helpers

Two tiny utilities the rest of the harness leans on: a shell runner that never throws, and a text extractor.

import Anthropic from "@anthropic-ai/sdk";
import { readFileSync, writeFileSync, existsSync } from "node:fs";
import { execSync } from "node:child_process";

const client = new Anthropic();              // reads ANTHROPIC_API_KEY
const MODEL = "claude-opus-4-8";

// run a shell command; capture output instead of crashing on non-zero exit
const sh = (cmd: string): string => {
  try { return execSync(cmd, { encoding: "utf8", stdio: ["ignore", "pipe", "pipe"] }); }
  catch (e: any) { return `ERROR: ${e.stdout ?? ""}${e.stderr ?? e.message}`; }
};

// pull the plain-text blocks out of a model response
const textOf = (m: Anthropic.Message): string =>
  m.content.filter(b => b.type === "text").map(b => (b as any).text).join("\n");

STEP 2 Durable state on disk

The whole point: state survives a context reset because it lives in progress.json and git, not in the window.

type Feature = { id: string; title: string; done: boolean };
type State   = { goal: string; features: Feature[]; notes: string[] };

const STATE_FILE = "progress.json";
const loadState = (): State => JSON.parse(readFileSync(STATE_FILE, "utf8"));
const saveState = (s: State) => writeFileSync(STATE_FILE, JSON.stringify(s, null, 2));

function saveProgress(note: string): string {
  const s = loadState(); s.notes.push(note); saveState(s);
  sh(`git add -A && git commit -q -m ${JSON.stringify("checkpoint: " + note)} || true`);
  return "progress saved + committed";
}
function markDone(id: string): string {
  const s = loadState(); const f = s.features.find(f => f.id === id);
  if (!f) return `no feature ${id}`;
  f.done = true; saveState(s); return `marked ${id} done`;
}
// evaluator gaps (Step 7) re-enter the feature list here
function reopenFeatures(gaps: string[]): void {
  const s = loadState();
  gaps.forEach((g, i) => s.features.push({ id: `fix-${s.features.length + i}`, title: g, done: false }));
  saveState(s);
}

STEP 3 Declare the tools (the hands)

Tools are the only way the model touches the world. Five are enough to build and verify a service.

const tools: Anthropic.Tool[] = [
  { name: "read_file",  description: "Read a file from the project",
    input_schema: { type: "object", properties: { path: { type: "string" } }, required: ["path"] } },
  { name: "write_file", description: "Create or overwrite a file",
    input_schema: { type: "object", properties: { path: { type: "string" }, content: { type: "string" } },
      required: ["path", "content"] } },
  { name: "run_bash",   description: "Run a shell command (build, start server, curl it)",
    input_schema: { type: "object", properties: { cmd: { type: "string" } }, required: ["cmd"] } },
  { name: "update_progress",   description: "Note progress and commit",
    input_schema: { type: "object", properties: { note: { type: "string" } }, required: ["note"] } },
  { name: "mark_feature_done", description: "Mark one feature id complete",
    input_schema: { type: "object", properties: { id: { type: "string" } }, required: ["id"] } },

STEP 4 Route tool calls to real code

One switch maps each tool name to an actual effect, reusing the Step 1-2 helpers. This is where "decide" becomes "act."

async function dispatchTool(name: string, input: any): Promise<string> {
  switch (name) {
    case "read_file":
      return existsSync(input.path) ? readFileSync(input.path, "utf8") : `no file ${input.path}`;
    case "write_file":
      writeFileSync(input.path, input.content); return `wrote ${input.path}`;
    case "run_bash":
      return sh(input.cmd);
    case "update_progress":
      return saveProgress(input.note);
    case "mark_feature_done":
      return markDone(input.id);
    default:
      return `unknown tool: ${name}`;
  }
}

Tutorial

STEP 5 The agent loop

The engine from slide 5, in code: call the model, run whatever tools it asked for, feed results back, repeat until it stops or hits the turn budget.

async function runAgentLoop(
  system: string, messages: Anthropic.MessageParam[], maxTurns = 60,
): Promise<Anthropic.Message> {
  let last!: Anthropic.Message;
  for (let turn = 0; turn < maxTurns; turn++) {
    last = await client.messages.create({ model: MODEL, max_tokens: 8192, system, tools, messages });
    messages.push({ role: "assistant", content: last.content });
    if (last.stop_reason !== "tool_use") break;          // model is done thinking

    const results: Anthropic.ToolResultBlockParam[] = [];
    for (const b of last.content) {
      if (b.type !== "tool_use") continue;
      results.push({ type: "tool_result", tool_use_id: b.id, content: await dispatchTool(b.name, b.input) });
    }
    messages.push({ role: "user", content: results });            // observation back into context
  }
  return last;
}

STEP 6 Worker prompt, handoff, reset

Each session() is a fresh window. build() keeps spawning sessions until every feature is done: that is the reset-and-handoff outer loop.

const SYSTEM = `You are a coding agent resuming a long task.
First, read progress.json and run \`git log --oneline\`.
Pick the SINGLE highest-priority unfinished feature.
Implement it, run the server and curl it to prove it works, commit,
then call mark_feature_done. Do NOT try to build everything at once.`;

const handoffPrompt = (s: State): string =>
  `Goal: ${s.goal}\n` +
  `Unfinished: ${s.features.filter(f => !f.done).map(f => `[${f.id}] ${f.title}`).join("; ")}\n` +
  `Recent commits:\n${sh("git log --oneline -8")}`;

async function session(): Promise<"more" | "complete"> {
  const s = loadState();
  if (s.features.every(f => f.done)) return "complete";
  await runAgentLoop(SYSTEM, [{ role: "user", content: handoffPrompt(s) }], 40);
  return "more";                                  // window ends; state is on disk
}
async function build(): Promise<void> {
  while ((await session()) === "more") console.log("↻ reset → fresh session, state reloaded");
}

Tutorial

STEP 7 An independent evaluator

A second agent with its own criteria probes the running service and returns JSON. Its gaps feed back through reopenFeatures() from Step 2.

const CRITERIA = ["functionality", "error handling", "code clarity"];

async function evaluate(): Promise<{ pass: boolean; gaps: string[] }> {
  const res = await runAgentLoop(
    `You are an INDEPENDENT evaluator. Start the server with run_bash and probe it
     with curl (POST /shorten, follow a redirect, hit an unknown code).
     Grade it on: ${CRITERIA.join(", ")}.
     Reply with ONLY JSON: {"pass": boolean, "gaps": string[]}.`,
    [{ role: "user", content: "Evaluate the current build against the goal in progress.json." }],
  );
  try { return JSON.parse(textOf(res).match(/\{[\s\S]*\}/)?.[0] ?? "{}"); }
  catch { return { pass: false, gaps: ["evaluator output was not valid JSON"] }; }
}

Tutorial

STEP 8 Seed the spec, then tie it together

seed() writes the feature list on the first run (the "initializer"). main() alternates build and evaluate until it passes.

function seed() {
  const state: State = {
    goal: "URL shortener in plain Node: POST /shorten {url}->{code}, GET /:code -> 302 redirect.",
    features: [
      { id: "f1", title: "HTTP server on PORT with a small router", done: false },
      { id: "f2", title: "POST /shorten stores the url, returns a short code", done: false },
      { id: "f3", title: "GET /:code 302-redirects to the original url", done: false },
      { id: "f4", title: "persist code->url map to store.json", done: false },
      { id: "f5", title: "404 unknown code, 400 bad input", done: false },
    ], notes: [],
  };
  saveState(state);
  sh("git init -q && git add -A && git commit -q -m 'seed: spec + progress'");
}

async function main() {
  if (!existsSync(STATE_FILE)) seed();             // run 1 only
  for (let round = 1; round <= 5; round++) {
    await build();                              // worker: build until all features done
    const v = await evaluate();                   // independent QA
    console.log(`round ${round}: ${v.pass ? "PASS" : "gaps -> " + v.gaps.join(", ")}`);
    if (v.pass) return;
    reopenFeatures(v.gaps);                      // gaps become new features, loop again
  }
}
main();   // run:  ANTHROPIC_API_KEY=... npx tsx harness.ts

Where to go next

You just built every core piece

  • You have the loop, tools, durable state, reset/handoff, and an independent evaluator. That is a real harness.
  • Level it up: run tools in a real sandbox, add tools over MCP, keep an append-only session log, parallelize workers, add guides and sensors (linters, type checks) as you hit recurring failures.
  • Keep it minimal. Delete any piece the model stops needing.

Wrap

A harness turns a model into a worker

  • One-shot answers. Chains run a script. A harness gives the model a loop, tools, memory, and a way to recover.
  • It buys you long, open-ended, real-world work that a single call cannot do.
  • Build the smallest one that works, prove each part earns its place, and strip it back as the model grows.
